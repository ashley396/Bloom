# AGENTS.md

## Cursor Cloud specific instructions

### What this is
Bloom / Floravia is a florist SaaS: a vanilla-JS single-page frontend in `public/`, ~40
Netlify serverless functions in `netlify/functions/`, backed by Supabase (Postgres + Auth)
with SQL in `supabase/`. There is also a small standalone `local-ai-bridge/` Ollama proxy
(optional). Stripe / Cloudflare AI / Google Maps are optional integrations. There is no
build step and no test framework; `npm run check` is a `node --check` syntax pass over all
JS files.

### Running it (local dev)
The dev environment needs Docker + local Supabase + the Netlify CLI. Docker, the Supabase
CLI, and `netlify-cli` are pre-installed in the VM snapshot (not via `npm install`).

1. Bring up services + database (idempotent, safe to re-run): `bash scripts/cloud-dev-up.sh`
   - Starts `dockerd` (see gotchas), runs `supabase start`, applies the schema, and writes `.env`.
2. Run the app: `netlify dev --offline --port 8888` (from the repo root).
   - App: http://localhost:8888  ·  Supabase Studio: http://localhost:54323
   - Health check: `curl -s http://localhost:8888/api/health` → `{"ok":true,...}`.

`netlify dev` is required (not opening `public/index.html` directly): the SPA calls `/api/*`,
which only works through the `netlify.toml` redirect to `/.netlify/functions/:splat`.
Use `--offline` to avoid Netlify account/login prompts.

### Non-obvious gotchas
- Docker has no init system here. `dockerd` is started manually (the bootstrap script does
  this) and configured for this nested VM with the `fuse-overlayfs` storage driver +
  `containerd-snapshotter` disabled (`/etc/docker/daemon.json`). The script also `chmod 666`
  the docker socket so `supabase`/`docker` work without `sudo`. Do NOT run `supabase` with
  `sudo` — that makes `supabase/.temp` root-owned and crashes the `netlify dev` file watcher
  (`EACCES watch .../supabase/.temp`). If that happens: `sudo chown -R $(id -un) supabase/.temp`.
- The repo's SQL is split across three inconsistent lineages: `supabase/schema.sql` (base
  tables + a signup trigger, `owner_id`), `supabase/migrations/v4.1..v8.0.sql` and the
  root `supabase/migration_v*.sql` incrementals, and `migration_floravia_saas_foundation_v1.sql`
  (adds `status`, `shop_subscriptions`, etc.). `scripts/cloud-dev-up.sh` applies them in the
  one correct order and adds two compatibility columns the current app code expects but the
  base schema lacks: `shop_members.status` (required by `_shared/supabase.js currentUser()`,
  and must exist before the Floravia migration whose SQL functions reference it) and
  `shops.updated_at`. It then GRANTs privileges to `anon/authenticated/service_role`
  (tables created directly via `psql` do not get Supabase's automatic grants).
- `.env` is gitignored and regenerated by the bootstrap script from `supabase status`. The
  local anon/service-role keys are the standard Supabase demo JWTs (stable while
  `supabase/config.toml` is unchanged). The data functions use the service-role key and
  bypass RLS, so RLS policy differences between the SQL lineages don't affect them.
- Signup auto-provisions a shop + owner membership (`status=active`) + profile via the
  `on_auth_user_created` trigger, so a fresh signup immediately has a working tenant.
  Email confirmation is disabled locally, so signup returns a session right away.

### Known pre-existing frontend bug (NOT an environment problem)
The authenticated SPA at `/` (`public/index.html` + `public/app.js`) renders blank on `main`.
`app.js` calls `setAuthMode(false)` on load, which references `#signupFields` / `#createIntro`
/ etc. that were removed from `index.html` when v22 split auth into separate `login.html` /
`signup.html` pages; the resulting `TypeError: Cannot set properties of null (setting 'hidden')`
throws before `showApp()` runs. The backend, the `/api/*` functions, and the `login.html` /
`signup.html` pages all work correctly — verify features via those pages and the API rather
than the `/` dashboard until this code bug is fixed.
